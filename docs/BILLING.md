# 支付与业务边界

## 下单与通知

套餐按 monthly、quarterly、yearly 分别计价，金额以整数分存储。
下单使用幂等键，生成订单快照及收银台跳转地址。
当前实现使用 `/submit.php` GET 跳转：

- V1：`EPAY_PID`、`EPAY_KEY`，MD5 签名。
- V2：`EPAY_PID`、`EPAY_PRIVATE_KEY`、`EPAY_PUBLIC_KEY`，
  RSA-SHA256 签名；私钥用于请求，平台公钥用于验签。

`EPAY_URL` 为商户网关基础地址。各网关协议差异必须实测，
不能仅凭“V2”名称认定兼容。PEM 密钥需保留换行。

当前通知入口为 POST `/api/v1/billing/epay/callback`，
接受表单或 JSON；没有 GET 通知处理器。接入前确认服务商通知方法。
RSA 通知还检查时间戳，部署主机应保持时间同步。

同步返回 `/billing/result?order=...` 只用于展示状态，
不能凭浏览器跳转认定支付成功。成功通知需要签名和金额检查，
再在数据库事务中结算订单、激活或延长订阅。

## 状态与人工操作

订单包含 `PENDING`、`PAID`、`FAILED`、`EXPIRED` 等状态。
重复通知不能重复增加订阅。代码中的事务锁不等同于已完成
MySQL 高并发验收，需要针对重复通知及同用户多订单并发实测。

管理员补单接口：
`POST /api/v1/admin/orders/{order_id}/reconcile`。
操作前在支付平台核对真实流水、金额与订单，不得用补单模拟付款。

退款是人工工作流：申请登记后，管理员在支付平台完成退款，
再通过 `PATCH /api/v1/admin/refunds/{refund_id}` 登记结果及平台退款号。
系统目前不会调用支付平台退款 API。操作前核对订阅影响并保留审计依据。

## 上线前检查

- 正确支付金额激活一次订阅；重复通知不重复延期。
- 错误签名、错误金额、过期时间戳不能激活权益。
- 失败、过期订单及并发回调符合状态机预期。
- 回跳先于异步通知时显示真实待支付状态。
- 非管理员不能补单或退款；用户不能查询其他租户订单。
- 人工退款与补单具有可核对的平台流水和审计记录。
